# Vulkan Compute Inference on AMD BC-250 / gfx1013 (RDNA1) — Platform Facts for a PS5 MoE Streaming Engine

> **Status (2026-10-21):** ACTIVE WITH CORRECTIONS — BC-250 is a driver-tuning cousin only (verified plan C1: PS5 GPU is GFX10.3-class, not gfx1013).

Scope: verified platform facts for a PS5 MoE streaming engine build spec. The PS5 is said to be configured like an AMD BC-250 (gfx1013, RDNA1-class). All facts below are as of October 2026. Confirmed measurements are distinguished from claims; inline sources are given.

**Hardware identity note (verify against premise):** The BC-250 is an ASRock Rack mining board built around AMD's "Cyan Skillfish" APU — Zen 2 CPU + gfx1013 GPU, 16 GB GDDR6 unified. The community labels gfx1013 "RDNA 1.5" (informal): GFX10.1 ISA with RDNA2-style ray-tracing extensions (`image_bvh_intersect_ray`). [akandr/bc250](https://github.com/akandr/bc250) explicitly states the PS5's Oberon is RDNA 2 (gfx1030+), and the BC-250's Cyan Skillfish (gfx1013) "behaves like a GFX10.1-era variant — though exact die-level comparisons are speculative"; the "RDNA 1.5" label is informal shorthand, not an official AMD designation. However, Phoronix (Jan 2025) reported Cyan Skillfish "is the GFX10/RDNA variant that powers the Sony PS5" and that it is "basically RDNA1/GFX10 ... with added support for image_bvh_intersect_ray ray tracing instructions; LLVM seems to be calling this variant gfx1013." So the premise "PS5 uses gfx1013 (RDNA1)" is partially supported by Phoronix but contradicted by akandr's read (PS5 = gfx1030/RDNA2). Flag this conflict for the report writer.

## 1. GPU Memory Budget on BC-250 under Linux + TTM Changes (pages_limit, page_pool_size)

### Takeaway
On Linux the BC-250's 16 GB unified (UMA) pool is split CPU/GPU, and two independent kernel memory managers (the amdgpu GTT cap and the TTM page manager) each default to ~7.4 GiB (half of the ~14.8 GiB system RAM), which blocks models >~5 GB. Raising `ttm.pages_limit` (and `ttm.page_pool_size`) to `4194304` (16 GiB) is the confirmed fix; after tuning Vulkan sees ~16.5 GiB in two overlapping logical heaps, and the practical GPU-usable budget is ~13–14 GiB of the 16 GB (the rest is OS/CPU/compute).

### Cited Findings
- TTM defaults its page limit to half of system memory (`num_pages / 2`), which on this board's 14.8 GiB is about 7.4 GiB; the 14B and 10.7 GiB MoE both allocate more than that. `ttm.pages_limit=4194304` raises the limit to 16 GiB — [akandr/bc250-rocm](https://github.com/akandr/bc250-rocm)
- Two bottlenecks required kernel-level fixes before larger models ran: (1) GTT cap — `amdgpu` driver defaults to ~7.4 GiB, fix `ttm.pages_limit=4194304` (the legacy `amdgpu.gttsize` is deprecated on modern kernels; removing it actually increased GTT to 16 GiB); (2) TTM pages_limit — kernel TTM manager independently caps ~7.4 GiB, same fix. On Fedora 43 / kernel 6.18.9 this was the only additional tuning required — [akandr/bc250](https://github.com/akandr/bc250)
- Runtime + persistent fix: `echo 4194304 | sudo tee /sys/module/ttm/parameters/pages_limit` and `.../page_pool_size`, plus `/etc/modprobe.d/ttm-gpu-memory.conf` with `options ttm pages_limit=4194304 page_pool_size=4194304` — [akandr/bc250](https://github.com/akandr/bc250)
- Gotcha: a silent 12 GiB cap — `systemd-tmpfiles` runs after boot and silently overwrites earlier cmdline/modprobe values; precedence order that bites: cmdline → modprobe → **tmpfiles wins last**. Verify `cat /sys/module/ttm/parameters/pages_limit` reads `4194304` (16 GiB), not `3145728` (12 GiB) — [akandr/bc250](https://github.com/akandr/bc250)
- elektricM docs give a "maximum GPU memory access (14.5–14.75 GB)" recipe via the ttm pair (`ttm.pages_limit` + `ttm.page_pool_size`, set from the docs' GB×1024×1024/4 formula), and advise "Limit usage to 14.25–14.5 GB in applications to avoid crashes". **S5 PRUNE 2026-10-21: the `amdgpu.gttsize=14750` token once quoted here was fabricated (STATE F12/W5 — the guide prescribes the ttm pair, not gttsize).** — [elektricM/amd-bc250-docs — Kernel Configuration](https://elektricm.github.io/amd-bc250-docs/linux/kernel/); also [Performance Issues](https://elektricm.github.io/amd-bc250-docs/troubleshooting/performance/)
- akandr's own read: "The real ceiling is ~13 GiB of model+KV, set by the 16 GB physical RAM (weights + KV + compute + OS), not by pages_limit. A ~14 GiB model (Mistral-Small Q4) still won't run — but for the physical-RAM reason, not a software cap" — [akandr/bc250](https://github.com/akandr/bc250)
- akandr/bc250-rocm describes the board as "around 14 GiB of usable shared memory" — [akandr/bc250-rocm](https://github.com/akandr/bc250-rocm)
- TechMakesArt treats the practical budget as "~13 GB of 14 GB budget" (Gemma 4 26B-A4B footprint ~13 GB of 14 GB) — [TechMakesArt/llama.cpp-bc250](https://github.com/TechMakesArt/llama.cpp-bc250)
- Without tuning, models over ~5 GB fail to load; defaults cap GPU buffers at 50% of system RAM (~7.4 GB) — [TechMakesArt/llama.cpp-bc250](https://github.com/TechMakesArt/llama.cpp-bc250)

### Inferences
- The "~14 GB budget of 16 GB" is a practical, not a hard, figure: ~13 GiB model+KV is the confirmed working ceiling (weights + KV + compute + OS), while the driver/GTT level can be raised to 14.5–14.75 GB max. A streaming engine should budget ~13 GiB for weights+KV and treat 14.5 GB as the absolute driver ceiling.
- `page_pool_size` must be set alongside `pages_limit`; both must be persisted via modprobe/tmpfiles AND verified live because of the silent 12 GiB overwrite trap.

### Gaps
- No source reports a single canonical "14 GB" figure; the ~14 GB figure is an aggregate of "~13 GiB working ceiling" (akandr), "~13 GB of 14 GB budget" (TechMakesArt), and "14.5–14.75 GB max driver access" (elektricM). The exact usable-budget number depends on stack and OS overhead and is not uniformly confirmed.

## 2. Vulkan Memory Types RADV Exposes on gfx1013 / BC-250; VK_EXT_external_memory_host

### Takeaway
RADV on gfx1013 reports the BC-250 as an INTEGRATED_GPU (Vulkan 1.4.328) and, after TTM tuning, exposes ~16.5 GiB in two overlapping logical heaps — device-local 8.33 GiB + host-visible 8.17 GiB — which are different views of the same 16 GB UMA pool (not additive). RADV implements VK_EXT_external_memory_host (gated on `has_userptr`), importing host pointers into the GTT-cached memory type, which is directly relevant to zero-copy SSD-to-GPU landing on UMA.

### Cited Findings
- After tuning, "Vulkan sees 16.5 GiB (two logical heaps backed by the same 16 GB physical pool — not additive)"; memory layout table: "Vulkan logical heaps 16.5 GiB — Device-local 8.33 GiB + Host-visible 8.17 GiB — overlapping views of the same 16 GB pool" — [akandr/bc250](https://github.com/akandr/bc250)
- `vulkaninfo --summary` reports `GPU0: AMD BC-250 (RADV GFX1013), Vulkan 1.4.328, INTEGRATED_GPU` — [akandr/bc250](https://github.com/akandr/bc250)
- RADV splits the device-local memory heap into two: one host-visible and one not, so clients can tell how much host-visible vs non-host-visible memory is available (heap 0 = vram_size − visible_vram_size, DEVICE_LOCAL; heap 1 = visible_vram_size, DEVICE_LOCAL; heap 2 = gart_size) — [Mesa-dev patch: radv split the device local memory heap into two](https://lists.freedesktop.org/archives/mesa-dev/2016-October/133476.html)
- RADV implements VK_EXT_external_memory_host: `vkGetMemoryHostPointerPropertiesEXT` reports the GTT_CACHED memory type for `VK_EXTERNAL_MEMORY_HANDLE_TYPE_HOST_ALLOCATION_BIT_EXT`; `radv_alloc_memory` with host_ptr_info creates a BO from the host pointer via `buffer_from_ptr`; `minImportedHostPointerAlignment = 4096`; extension gated on `device->rad_info.has_userptr` — [Mesa-dev patch: radv implement VK_EXT_external_memory_host](https://lists.freedesktop.org/archives/mesa-dev/2018-February/184320.html); [sailfishos-mirror/mesa radv_device.c](https://github.com/sailfishos-mirror/mesa/blob/4235c39a/src/amd/vulkan/radv_device.c)
- VK_EXT_external_memory_host enables importing host allocations and host-mapped foreign device memory into Vulkan memory objects; RADV's implementation is based on RadeonSI's AMD_pinned_memory — [Phoronix: RADV Vulkan Driver Now Exposes VK_EXT_external_memory_host](https://www.phoronix.com/news/RADV-External-Host-Memory); [Vulkan ref page](https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_external_memory_host.html)
- On UMA, memory is advertised DEVICE_LOCAL | HOST_VISIBLE, so no staging buffer is needed and transfer overhead is reduced — [Vulkan memory allocation guide](https://docs.vulkan.org/guide/latest/memory_allocation.html)

### Inferences
- For a zero-copy SSD-to-GPU landing path, VK_EXT_external_memory_host is the right primitive: RADV maps host pointers into the GTT-cached (host-visible) memory type, which on this UMA device is also device-visible — so a host allocation (e.g., an NVMe-buffered page) can be imported and read directly by the GPU without a staging copy. The 8.17 GiB host-visible heap is the practical target for host-pinned landing buffers.
- The two "overlapping" heaps (8.33 + 8.17 ≈ 16.5 GiB) are not additive; a streaming engine must budget against the single 16 GB physical pool (~13 GiB usable).

### Gaps
- No source explicitly confirms VK_EXT_external_memory_host is advertised/enabled on gfx1013 specifically (the Mesa patch gates it on `has_userptr`); its availability on the BC-250/RADV gfx1013 build is inferred from RADV's general implementation, not directly measured on this chip. Recommend an on-target `vulkaninfo`/CTS check.

## 3. llama.cpp ggml-vulkan Shader Changes for gfx1013 (TechMakesArt/llama.cpp-bc250)

### Takeaway
The TechMakesArt fork (pinned to upstream f772f6e43 / b8819, snapshot, not maintained) makes three ggml-vulkan changes for gfx1013: (1) `rm_kq=4` on RDNA1 (+3% tg across K-quants), (2) a Q4_K `smin` algebraic restructure (+3% tg), and (3) a fused gate+up+SwiGLU_Split Vulkan kernel for Q4_K (+5.8% tg). Combined they lift Qwen3.5-9B Q4_K_M decode from 37.0 to ~42.3 tok/s, with the SMU governor adding the remaining ~29.7% to reach 54.99 tok/s.

### Cited Findings
- Change 1 — `rm_kq = 4` on RDNA1 (matches GCN tuning), file `ggml/src/ggml-vulkan/ggml-vulkan.cpp`: upstream defaults rm_kq (rows per workgroup for K-quants) to 2 on RDNA1 while GCN uses 4; on gfx1013 + RADV, rows-per-workgroup=4 gives +3% tg across all K-quants (Q2_K–Q6_K) with no register spills and unchanged perplexity. Caveat: arch × driver specific — PR #21043 found rm_kq=1 best on AMDVLK/RDNA4; change applies only to `architecture == AMD_RDNA1` — [TechMakesArt/llama.cpp-bc250](https://github.com/TechMakesArt/llama.cpp-bc250)
- Change 2 — Q4_K smin algebraic restructure, file `vulkan-shaders/mul_mat_vec_q4_k.comp`: the `smin` sum is rewritten from 16 FMAs into 4 horizontal-sum + 4 FMA form (same identity `mul_mat_vec_q5_k.comp` already uses). +3% tg across all Q4_K workloads. Cleanest upstream PR candidate: 6 lines, no arch-specific code — [TechMakesArt/llama.cpp-bc250](https://github.com/TechMakesArt/llama.cpp-bc250)
- Change 3 — Fused gate+up+SWIGLU_SPLIT Vulkan kernel (Q4_K only): new files `mul_mat_vec_glu_iface.glsl`, `mul_mat_vec_glu_base.glsl`, `mul_mat_vec_q4_k_glu.comp`, `vulkan-shaders-gen.cpp` (+18), `ggml-vulkan.cpp` (+~200). Detects the `MUL_MAT(gate,cur) + MUL_MAT(up,cur) + SWIGLU_SPLIT` pattern emitted by Llama/Qwen/Gemma-family FFNs; reads `cur` once (not twice) and writes SwiGLU output directly. Activates only for Q4_K weights, shared cur, single-column decode (`ne11==1`), `GGML_GLU_OP_SWIGLU`; falls back to two-MUL_MAT otherwise. +5.8% tg. Disable via `GGML_VK_DISABLE_FUSION=1` — [TechMakesArt/llama.cpp-bc250](https://github.com/TechMakesArt/llama.cpp-bc250)
- Stepwise contribution on Qwen3.5-9B Q4_K_M (Ubuntu 24.04, kernel 6.8.0, Mesa 26.0.3, RADV, TTM raised to 16 GiB): baseline 37.00 → +fused gate+up 39.15 (+5.8%) → +Q4_K smin 41.08 (+5.2%) → +RDNA1 rm_kq=4 42.33 (+3.0%) → +SMU governor 54.99 (+29.7%) — [TechMakesArt/llama.cpp-bc250](https://github.com/TechMakesArt/llama.cpp-bc250)
- Perplexity validated unchanged within noise (±0.025 on wikitext fragment); `test-backend-ops MUL_MAT` passes 938/938 on Vulkan — [TechMakesArt/llama.cpp-bc250](https://github.com/TechMakesArt/llama.cpp-bc250)
- Fork is pinned to f772f6e43 (b8819) and will not be rebased; upstream PR candidates: smin restructure (Tier 1), rm_kq=4 and fused gate+up (Tier 2, need broader hardware testing) — [TechMakesArt/llama.cpp-bc250](https://github.com/TechMakesArt/llama.cpp-bc250)

### Inferences
- The fused gate+up kernel is Q4_K-specific and decode-only (single-column); batched prefill (`NUM_COLS > 1`) falls back to upstream. A streaming engine targeting Q4_K decode can adopt these three changes; IQ/NL/other quants only benefit from the SMU governor, rm_kq=4, and the smin fix.
- The rm_kq=4 and fusion changes are arch/driver-tuned (RADV gfx1013); they may regress under AMDVLK or other RDNA1 cards, so porting to a PS5-specific build needs A/B validation.

### Gaps
- No source documents these shader changes being merged upstream as of Oct 2026; the fork itself is a snapshot and "not actively maintained." Upstream status of the three changes is unconfirmed.

## 4. Quant Format Performance on gfx1013 (Q4_K_M vs IQ4_XS vs IQ3_S); IQ4_XS Penalty Consensus

### Takeaway
On gfx1013 (b8819, governor on) measured decode is essentially bandwidth-bound: Q4_K_M 54.99 tok/s, Q4_K_S 55.39 (+0.7%), IQ4_NL 54.19 (−1.5%), IQ4_XS 42.39 (−23%), Q5_K_M 47.19 (−14%), Q6_K 44.38 (−19%), Q8_0 32.46 (−41%); effective bandwidth ~290 GB/s (~65% of 448 GB/s peak). The IQ4_XS penalty was a per-block decode-path cost on gfx1013 without int-dot instructions, but it has since been fixed in later llama.cpp builds (b10727: IQ4_XS now speed-parity with Q4_K_S), so the "−23% penalty" is a build-specific artifact, not a permanent hardware limitation.

### Cited Findings
- TechMakesArt quant table on Qwen3.5 9B, same binary, governor on, `llama-bench -p 512 -n 128`: IQ4_XS 4.80 GiB 42.39 (−23%), IQ4_NL 4.99 GiB 54.19 (−1.5%), Q4_K_S 5.01 GiB 55.39 (+0.7%), Q4_K_M 5.28 GiB 54.99 (ref), Q5_K_M 6.12 GiB 47.19 (−14%), Q6_K 6.94 GiB 44.38 (−19%), Q8_0 8.86 GiB 32.46 (−41%) — [TechMakesArt/llama.cpp-bc250](https://github.com/TechMakesArt/llama.cpp-bc250)
- "Every quant from IQ4_NL through Q8_0 ends up at roughly the same effective memory bandwidth (~290 GB/s, about 65% of the 448 GB/s peak). That means tok/s is essentially just the inverse of file size"; "Avoid IQ4_XS: despite being in the IQ family it falls off a cliff on gfx1013 — the per-block decode path is expensive without int-dot instructions, costing 23% throughput for only 0.2 GiB savings" — [TechMakesArt/llama.cpp-bc250](https://github.com/TechMakesArt/llama.cpp-bc250)
- Discussion #28226 (b10727, Sep 2026): "a Qwen3.6-35B-A3B MoE across three boards does pp 559 t/s / tg 68 t/s (IQ4_XS — which, fun fact, is now speed-parity with Q4_K_S on this build; the old −23% i-quant decode penalty we measured on b10405 is gone)" — [llama.cpp Discussion #28226](https://github.com/ggml-org/llama.cpp/discussions/28226)
- Upstream Vulkan IQ4_XS dequant was improved: PR #20657 "vulkan: dequantize iq4_xs 4 at a time" merged 2026-03-19 (RX 470: 2.42 TFLOPS vs 2.25 master) — [llama.cpp PR #20657](https://github.com/ggml-org/llama.cpp/pull/20657)
- IQ3_S is used in the 122B cluster as a smaller/lower-bit quant (Qwen3.5-122B-A10B IQ3_S, 43 GiB) — [llama.cpp Discussion #28226](https://github.com/ggml-org/llama.cpp/discussions/28226)

### Inferences
- On gfx1013 decode is bandwidth-bound, so quant choice is a quality-per-bit tradeoff, not a speed lever: bigger file ⇒ fewer tok/s at the same ~290 GB/s. Q4_K_M is the recommended default; IQ4_NL is the size-alternative at near-parity speed.
- The IQ4_XS penalty consensus is time-dependent: as of b8819 it was −23% on gfx1013, but by b10727 (Sep 2026) it is speed-parity with Q4_K_S. A streaming engine should re-benchmark IQ4_XS on its own build rather than assume the old penalty.

### Gaps
- No direct single-node IQ3_S vs IQ4_XS vs Q4_K_M controlled comparison on gfx1013 exists in the sources; the IQ3_S figure is only from the 122B cluster context. The "IQ4_XS penalty gone" claim is from one cluster operator's measurement, not an independent benchmark.

## 5. Measured Decode tok/s on BC-250 (Qwen3.5-9B, Gemma 4 26B-A4B, Qwen3.5-122B-A10B)

### Takeaway
Decode throughput is strongly clock- and stack-dependent: Qwen3.5-9B Q4_K_M hits 54.99 tok/s on the TechMakesArt fork + SMU governor (vs 23.1 tok/s stock Ollama at 24-CU/1500 MHz, or 31.1 at 40-CU); Gemma 4 26B-A4B (UD-Q3_K_M) reaches 69.66 tok/s single-node; Qwen3.5-122B-A10B (IQ3_S, 43 GiB) across a 4-node RPC cluster reaches 29.5 tok/s generation with FA-on + forced shmem_staging (19.0 without). These are measurements from specific builds/boards, not vendor figures.

### Cited Findings
- Qwen3.5-9B Q4_K_M (TechMakesArt fork, SMU governor, RADV): single-stream tg 54.99 tok/s (+48.6% vs stock 37.00), pp ~306 (+53%), batched-32 aggregate tg 151, batched-64 aggregate tg 175 — [TechMakesArt/llama.cpp-bc250](https://github.com/TechMakesArt/llama.cpp-bc250)
- Qwen3.5-9B Q4_K_M (akandr, Ollama 0.20, 24-CU, oberon 1500 MHz): 23.1 tok/s; at 40-CU unlock: 31.1 tok/s (+1.34×) — [akandr/bc250](https://github.com/akandr/bc250)
- Gemma 4 26B-A4B (MoE, 25.2B total / ~4B active), UD-Q3_K_M, KV q8_0, single node: decode tg128 69.66 tok/s, pp512 449.76 tok/s, usable context 24k, memory footprint ~13 GB of 14 GB budget — [TechMakesArt/llama.cpp-bc250](https://github.com/TechMakesArt/llama.cpp-bc250)
- Gemma 4 26B MoE over RPC across two boards: pp 508 t/s / tg 73.5 t/s (IQ3_S) — [llama.cpp Discussion #28226](https://github.com/ggml-org/llama.cpp/discussions/28226)
- Qwen3.5-122B-A10B (IQ3_S, 43 GiB) across 4 nodes + dirigent, context 28k: FA off → prefill 96 t/s, generation 19.0 t/s; FA on + forced shmem_staging → prefill 162 t/s (+68%), generation 29.5 t/s (+55%) — [llama.cpp Discussion #28226](https://github.com/ggml-org/llama.cpp/discussions/28226)
- Price/perf comparison (community numbers): 5x BC-250 ~$500 → 29.5 t/s; Ryzen AI Max 395 (Strix Halo 128GB) ~$2,000 → 28.5 t/s FP4; Mac Studio M3 Ultra 256GB ~$5,600 → 57 t/s; Mac Mini M4 Pro 64GB ~$2,000 → ~2 t/s — [llama.cpp Discussion #28226](https://github.com/ggml-org/llama.cpp/discussions/28226)
- MoE-on-scalar-hardware observation (akandr, IQ2_M, llama.cpp, 24-CU): Qwen3.x A3B MoEs (30–35B total / 3B active) decode 58–60 tok/s; dense QwQ-32B at same IQ2_M only 9.6 tok/s (~6× gap); MoE leads 14B dense by ~14–25% — [akandr/bc250](https://github.com/akandr/bc250)

### Inferences
- For a PS5 MoE streaming engine, decode speed scales with active parameters (bandwidth-bound): a 26B-A4B MoE decodes near a 4B dense model's rate. The 122B-A10B cluster figure (29.5 t/s) includes RPC network tax and a 4-node split; single-node throughput is higher for smaller MoEs.
- The single biggest controllable lever is the SMU governor (clock), then the 40-CU unlock (~1.32× gen); the TechMakesArt shader changes add ~5-11% on top. Figures vary ~2× between stock-Ollama and fork+governor configs, so any build spec must pin the exact stack.

### Gaps
- The 122B-A10B figure is a 4-node RPC cluster number, not single-node; no single-node 122B decode figure exists on BC-250. The Qwen3.5-9B figure is from the TechMakesArt fork (b8819) and differs from akandr's Ollama numbers due to clock + Ollama-vs-llama.cpp differences.

## 6. SMU Clock Governor Speedup (~+29.7%) and Speculative Decoding

### Takeaway
The community SMU governor (cyan-skillfish-governor-smu, filippor/Magnap/bc250-collective) is the single biggest performance win on BC-250: it drives clocks through SMU firmware calls (no kernel patch), lifting the stock 1500 MHz pin to 2300+ MHz, and TechMakesArt measured +29.7% tg on Qwen3.5-9B Q4_K_M from it. Speculative decoding does NOT deliver on BC-250 (Vulkan): high draft acceptance (72%) still yields no wall-clock gain because the Vulkan batched-verify path is the bottleneck.

### Cited Findings
- "The biggest single performance win on BC-250 comes from something that is not in this fork: the community SMU governor, which unlocks GPU clocks past the amdgpu driver's conservative ceiling. ... The amdgpu driver pins gfx1013 shader clock at 1500 MHz even under sustained compute. The chip can hold 2300+ MHz stably." — [TechMakesArt/llama.cpp-bc250](https://github.com/TechMakesArt/llama.cpp-bc250)
- Stepwise contribution: "+ SMU governor: 54.99 (+29.7%) ← biggest single win, and it's someone else's work" — [TechMakesArt/llama.cpp-bc250](https://github.com/TechMakesArt/llama.cpp-bc250)
- Governor comparison (elektricM docs): None = 1500 MHz fixed; SMU = Variable, 2300+ MHz, 0.9–1.3% CPU, 24 ms response, no kernel patch; TT = 2175+ MHz, kernel patch; Oberon (legacy) = 1000–2000 MHz, 100 ms response — [elektricM/amd-bc250-docs — GPU Governor Setup](https://elektricm.github.io/amd-bc250-docs/system/governor/)
- SkillFishOS: governor idle 350 MHz / 700 mV, load 2230 MHz / ~1000 mV; "Unlocked 40 CUs, a governor pushing the GPU to 2230 MHz and CPU overclock+undervolt: +34% real performance from the very same chip" — [SkillFishOS hardware](http://www.skillfishos.com/en/hardware/); [SkillFishOS performance](https://www.skillfishos.com/en/docs/prestazioni/)
- Speculative decoding (TechMakesArt, Vulkan): Qwen3.5 9B hybrid (Gated Delta Net) blocks partial sequence removal — `llama-server` refuses to initialize speculative; CLI compat check passes but draft acceptance collapses to ~0.8% on a 0.8B draft. Llama 3.1 8B + Llama 3.2 1B: 72% draft acceptance measured, but total wall-clock throughput identical to non-speculative (~55 tok/s both); theoretical math predicted ~1.9×. "The gap points at the Vulkan backend's batched verify path, not BC-250 itself." — [TechMakesArt/llama.cpp-bc250](https://github.com/TechMakesArt/llama.cpp-bc250)

### Inferences
- A PS5 MoE streaming engine should treat the SMU governor as mandatory infrastructure (clock is the biggest decode lever), but note the governor requires a community-patched BIOS (Robin 3.00) and conflicts with other governor services.
- Speculative decoding is unlikely to help on a Vulkan gfx1013 path until the Vulkan batched-verify path is improved; the bottleneck is the backend, not the silicon.

### Gaps
- The +29.7% figure is TechMakesArt's single measurement on one model/config; the governor's gain is workload-dependent (gaming +34%, compute +29.7% on one model). No independent confirmation of the exact +29.7% figure exists in the sources.

- gfx1013 = "Cyan Skillfish", 40 physical CUs but only 24 active stock (factory harvest mask); community kernel patch (duggasco/bc250-40cu-unlock) re-enables 16 more; 1536 SPs stock → 2560 SPs after unlock — [akandr/bc250](https://github.com/akandr/bc250); [elektricM 40-CU unlock](https://elektricm.github.io/amd-bc250-docs/system/40cu-unlock/)
- 40-CU unlock measured A/B (llama.cpp b9265, 4K ctx): median gen 1.32×, median prefill 1.50×; Qwen3.5-35B-A3B MoE 59.5 → 78.7 tok/s (+32%); roofline: peak streaming bandwidth 357 GB/s, peak FP32 3901 GFLOP/s, ridge point 10.9 FLOP/byte — all LLM decode quants sit left of ridge (bandwidth-bound) — [akandr/bc250](https://github.com/akandr/bc250)
- Mesa RADV gfx1013 support was added experimental in Mesa 25.1 (Phoronix, Mar 2025); earlier needed `RADV_DEBUG=nocompute` for Mesa < 25.1; compute queue on gfx1013 was "known to be broken" but a fix exists (DryhoppedIPA/bc250-gfx1013-fix: async-compute threadgroup bug, `has_async_compute_threadgroup_bug` for GFX1013) — [Phoronix](https://www.phoronix.com/news/Mesa-25.1-RADV-AMD-BC-250), [Phoronix Jan 2025](https://www.phoronix.com/news/AMD-RADV-PS5-BC-250), [DryhoppedIPA/bc250-gfx1013-fix](https://github.com/DryhoppedIPA/bc250-gfx1013-fix)
- ROCm/HIP on gfx1013: not usable as shipped (no gfx1013 solution libraries); works with patched kernel + native rocBLAS build; Vulkan is the simpler/faster inference path (~10× prompt-processing advantage) — [akandr/bc250-rocm](https://github.com/akandr/bc250-rocm)
- Memory bandwidth ceiling: TechMakesArt cites 448 GB/s GDDR6 theoretical peak (65% achieved); akandr roofline measured 357 GB/s peak streaming bandwidth — [TechMakesArt/llama.cpp-bc250](https://github.com/TechMakesArt/llama.cpp-bc250); [akandr/bc250](https://github.com/akandr/bc250) (note: these two ceiling figures differ and are measured vs theoretical)

## Source-quality notes
- TechMakesArt/llama.cpp-bc250 is a snapshot fork (pinned b8819, "not actively maintained") whose numbers are single-board measurements; its IQ4_XS −23% claim is superseded by later builds (b10727) per Discussion #28226.
- akandr/bc250 is the most rigorous (n=3 medians, A/B, full methodology paper at zenodo.org/records/21459691), but all figures are from one board (Fedora 43, Mesa 25.3.4, oberon 1500 MHz cap).
- Discussion #28226 is a single cluster operator's production measurement (Sep 2026); its IQ4_XS-parity and 122B figures are not independently confirmed.
- The "PS5 uses gfx1013 (RDNA1)" premise conflicts between Phoronix (Cyan Skillfish = PS5 silicon, RDNA1-class) and akandr (PS5 Oberon = RDNA2 gfx1030+, BC-250 gfx1013 = GFX10.1-era); flag for the report writer.
