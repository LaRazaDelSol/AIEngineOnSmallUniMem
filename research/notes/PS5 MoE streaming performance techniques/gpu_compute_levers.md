# GPU/Compute-Side Levers for MoE Decode on Oberon-class APU (gfx1013/gfx1030, 36 CU, 16 GB GDDR6) under Vulkan — Oct 2026

> **Status (2026-10-21):** ACTIVE evidence base — numbers are claims; re-derive against the W4 recompute before citing (the parent report had ledger arithmetic errors, W1/FLOW kill list).

Scope: compute-side techniques (kernels, dequant, CPU experts, overlap, memory budget, PS5 native-OS path). gfx1013 = BC-250/"Cyan Skillfish" (PS5-class silicon); gfx1030 = RDNA2 desktop. PS5 = 36 CU, ~2230 MHz with boost, ~448 GB/s peak / ~290 GB/s effective GDDR6.

## Q1. MoE kernels in ggml-vulkan: MUL_MAT_ID status, fused MoE FFN, expert-streaming work

### Takeaway
MUL_MAT_ID is functional and the hottest area of upstream Vulkan optimization in 2026: three mul_mat_id kernel-selection PRs landed or advanced Aug–Oct 2026, one validated *directly on BC-250/gfx1013* (+36% batched decode). A complete "pinned-experts-on-GPU pool + CPU-miss-correction" streaming design (BlobPager) measured 1.62x over `--cpu-moe` on a 16 GB card — the template for a streamed-expert engine. No merged `--moe-stream` flag exists upstream as of Oct 2026; streaming lives in forks/research threads.

### Cited findings
- **MUL_MAT_ID implemented in Vulkan** (🟡 partial coverage in ops matrix) — [ops.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/ops.md).
- **PR #27332 (open, Oct 2026): density gate for MUL_MAT_VEC_ID.** Replaces fixed `batch<=8` cutoff for the Vulkan matvec-id MoE path with routed-density heuristic (`n_tokens*experts_per_token <= 2*n_experts`, cap 64 tok). Validated on **gfx1013 (BC-250)**, gfx1151, RDNA3: **+36% at B=9, +27% at B=16, +21% at B=64, neutral at B≤8**; MUL_MAT_ID tests 872/872 on gfx1013. Forcing tiled path everywhere on gfx1013: −44% at tg64, ~−50% at B=1. Related: issue #25356 (batch-9 throughput cliff on RADV, many-expert MoE), PR #25862 (mul_mat_vec_id for 256-expert models; RADV tiled-shader pipeline-compile stall) — [PR #27332](https://github.com/ggml-org/llama.cpp/pull/27332)
- **PR #29182 (merged 2026-10-01, commit 94a0ae3): MoE-aware mul_mat_id tile selection** — picks tiles from per-expert row count instead of total tokens. On Strix Halo (Sarvam-30B Q4_K_M, 128 experts): prefill 384→~421 t/s (+10%), expert kernel −10–11%; tg flat (72.5→69.3 in-band). **Regression on RDNA4**: issue #29892 reports −12% pp2048 on RX 9070 XT (Qwen3.6-35B-A3B, 256 experts, n_per_expert=32; reverts cleanly; tg unaffected, 107.3 vs 107.1) — [PR #29182](https://github.com/ggml-org/llama.cpp/pull/29182), [issue #29892](https://github.com/ggml-org/llama.cpp/issues/29892)
- **PR #29998 (Oct 2026): handle mul_mat_id duplicate ids in a prepass** — compact tile-descriptor list, tighter workgroup upper bound, tail early-exit; alternative to #29822 — [PR #29998](https://github.com/ggml-org/llama.cpp/pull/29998)
- **BlobPager (discussion #29234): demand-paged MoE expert serving on one 16 GB consumer GPU.** Router on GPU → get_rows remap to 97-slot VRAM pool → gate/up/down mul_mat_id vs pool; misses computed on CPU full tensor in the same ubatch and added after the weighted sum. Qwen3-30B-A3B Q4_K_M (16.35 GiB experts vs 15.6 GiB usable): **1.622x over `--cpu-moe 48`** baseline (25.23 t/s tg128); pool of 11.99 GiB staged disk→VRAM in 1.61 s (pread 14.1 GB/s + H2D 18.5 GB/s); GPU pool mul_mat_id = 12.0 µs per 8-draw layer call vs **CPU miss path ~145 µs/expert draw**; "dead valley" of naive partial offload at 32–40 CPU layers (15.7–17.3 t/s) vs `--cpu-moe 12` = **50.31 t/s (+99%)** — [discussion #29234](https://github.com/ggml-org/llama.cpp/discussions/29234), repo [bdrazn/blobpager](https://github.com/bdrazn/blobpager)
- **No upstream `--moe-stream`; LOAD_MODE exists**: `LLAMA_ARG_LOAD_MODE=dio` (direct-IO model load) used in production on a 5×BC-250 cluster — [discussion #28226](https://github.com/ggml-org/llama.cpp/discussions/28226). `--n-cpu-moe` (PR #15077) and `-ot exps=CPU` (PR #11397) are the shipped expert-placement knobs — [ollama PR #16688](https://github.com/ollama/ollama/pull/16688), [PR #11397](https://github.com/ggml-org/llama.cpp/pull/11397)
- **Forks doing SSD expert streaming**: cecil-the-coder/llama-cpp-moe-flash (io_uring prefetch + double-buffered staging + MUL_MAT_ID_STREAMING shader variant on Strix Halo; 14 t/s PoC; cites upstream two-tier expert cache PR #20757, 10.4–11.1 t/s with 96 slots) — [repo](https://github.com/cecil-the-coder/llama-cpp-moe-flash), [design doc](https://github.com/cecil-the-coder/llama-cpp-moe-flash/blob/main/docs/design.md); xero00000/expert-streaming-engine (ik_llama.cpp fork: deferred-mmap expert weights, hybrid GPU-resident MoE layers, route-aware page-cache prefetch for F16/MXFP4 MoE on low-VRAM boxes) — [repo](https://github.com/xero00000/expert-streaming-engine/blob/chunked-gdn-port)
- **Fused FFN on gfx1013 specifically**: TechMakesArt/llama.cpp-bc250 (snapshot fork, "vulkan-fused-gate-up") fuses MUL_MAT(gate)+MUL_MAT(up)+SWIGLU into one `mul_mat_vec_q4_k_glu` kernel: **tg 37.00→54.99 t/s (+48.6%), pp 199.66→~306 t/s (+53%)** on BC-250 vs stock Vulkan, perplexity unchanged — [TechMakesArt/llama.cpp-bc250](https://github.com/TechMakesArt/llama.cpp-bc250)
- **Fork with 512-expert mul_mat_id work + MTP on Vulkan**: Qwen3.8-Flash-Next at 1M ctx on Strix Halo (RDNA3.5) reports 61 t/s empty / 45 t/s @524k decode, MTP ~1.5x on Vulkan, incl. radix top-k, indexed FA, mul_mat_id changes for 512 experts — [discussion #30282](https://github.com/ggml-org/llama.cpp/discussions/30282)
- Vulkan >> ROCm/HIP for MoE decode on integrated AMD: Strix Halo Qwen3-35B-A3B Q8_0 tg128 Vulkan 49.5 vs HIP 33.7 t/s (~149 vs ~101 GB/s effective; HIP undercounted FETCH_SIZE) — [issue #24438](https://github.com/ggml-org/llama.cpp/issues/24438); a second reporter saw HIP within 6–12% of Vulkan there.

### Inferences
- The MMV (matvec-id) path is the right kernel for streamed-expert decode at B=1–8 on gfx1013 (tiled path is −50% at B=1), and PR #27332's density gate is the concrete upstream patch to cherry-pick for the PS5 engine; it directly fixes the B=9 cliff that would hit any batched/spec verify path.
- BlobPager's numbers say: on 16 GB, keep a pinned expert pool sized ~75% of expert bytes (their 47×96-pin sweet spot), route misses to CPU for correctness — and *avoid* the 60–80% CPU-layer split (dead valley) that also appears in `--n-cpu-moe` sweeps.
- #29182's RDNA4 regression shows tile-selection tuning is architecture-sensitive; blindly trusting upstream selection on gfx1013/gfx1030 is risky — A/B on-target.

### Gaps
- No published tok/s for BlobPager-class streaming on gfx1013/gfx1030 itself (validation was on a 16 GB discrete card, likely RDNA2/3 — card model not stated in the discussion excerpt).
- No upstream fused MoE FFN (gate+up+swiglu+down) shader for Vulkan beyond SYCL's fused top-k MoE (#25217); the glu fusion exists only in the BC-250 snapshot fork.

## Q2. Low-bit dequant throughput on RDNA1 vs RDNA2 Vulkan; the int-dot gap

### Takeaway
The big 2026 dequant win — int8 coopmat quantized matmul (PR #27952) — is explicitly **gated to RDNA3/4**, so neither gfx1013 nor gfx1030 gets it; those parts stay on scalar/LUT MMQ+MMV paths where dequant is ALU work in parallel with bandwidth. Direct gfx1013 evidence says the i-quant *penalty* is gone at 4-bit on current builds (IQ4_XS parity with Q4_K_S since ~b10727), while RDNA2's DP4A (v_dot4/v_sadbit family) is exploited only in the flash-attention DP4A shader (#20797), not in MoE GEMV. On this silicon class, decode at 2-bit is bandwidth-bound, not dequant-bound.

### Cited findings
- **PR #27952 (merged, commit 70c4e15): int8 coopmat1 quantized matmul "for AMD RDNA3 and RDNA4"** — q8_0/q4_1/q5_0/q5_1/q3_k/q4_k/q5_k/q6_k/iq4_nl/iq4_xs/mxfp4/nvfp4, with mul_mat_id support; "only force subgroup size 32 on AMD RDNA", "gate to RDNA3/4". RX 7900 XTX (RDNA3) 27B data in issue #29342 — [commit](https://github.com/ggml-org/llama.cpp/commit/70c4e1582), [issue #29342](https://github.com/ggml-org/llama.cpp/issues/29342). gfx1013/gfx1030 report `matrix cores: none` (no coopmat), so this path is unavailable on PS5-class hardware.
- **DP4A in ggml-vulkan**: PR #20797 (merged ~Apr 2026) adds DP4A to the *scalar flash-attention* shader for quantized KV (q8_0/q4_0 pairs), enabled when the GPU supports it — [PR #20797](https://github.com/ggml-org/llama.cpp/pull/20797). Bug #17414: int dot silently disabled when `-fa 1` in some images — [issue #17414](https://github.com/ggml-org/llama.cpp/issues/17414). Vulkan exposes this via VK_KHR_shader_integer_dot_product (fastPath is a per-device perf promise) — [proposal](https://docs.vulkan.org/features/latest/features/proposals/VK_KHR_shader_integer_dot_product.html). Device strings: gfx1030-class iGPUs report `int dot: 1 | matrix cores: none` — [linux-ng blog](https://blog.linux-ng.de/2025-09-27/running-llms-with-llama-cpp-using-vulkan). No ggml-vulkan MoE GEMV uses int-dot; no source found showing gfx1013's int-dot capability string (RDNA1 ISA famously omits v_dot4_i32_i8 — treat gfx1013 as no-DP4A unless vulkaninfo on the PS5/BC-250 proves otherwise: **gap**).
- **What DP4A buys on AMD Vulkan when present**: hanzo-kernel reports int8 dp4a matvec on gfx1151 (RDNA3.5) at **196 GB/s = 118% of a hand-tuned fp16 kernel**, lowering to a single OpSDot, "2.35x a scalar loop" — [docs.rs/hanzo-kernel](https://docs.rs/crate/hanzo-kernel/latest).
- **gfx1013 i-quant measurements**: the 5×BC-250 cluster reports **IQ4_XS is speed-parity with Q4_K_S on current builds; the −23% i-quant decode penalty measured on b10405 is gone** — [discussion #28226](https://github.com/ggml-org/llama.cpp/discussions/28226).
- **BC-250 MoE vs dense at low bits**: Qwen3.x A3B MoEs (30–35B/3B active) decode **58–60 t/s at IQ2_M** vs QwQ-32B dense 9.6 t/s at same quant (24 CU, oberon governor capped 1500 MHz, llama.cpp b9265, Mesa 25.3.4) — [akandr/bc250](https://github.com/akandr/bc250/blob/main/Readme.md).
- **1-bit/ternary class**: Bonsai 1-bit models (Q1_0-ish) run **359/190/122 t/s (1.7B/4B/8B) on Strix Halo Radeon 8060S via stock llama.cpp Vulkan** (RDNA3.5, UMA); custom Q1_0 GPU kernels were needed for HIP — [Bonsai-demo issue #33](https://github.com/PrismML-Eng/Bonsai-demo/issues/33). No gfx1013/gfx1030 TQ1_0/TQ2_0/BitNet b1.58 Vulkan decode numbers found (**gap**); llama.cpp lists BitNet b1.58 among supported model families — [Aloereed fork README](https://github.com/Aloereed/llama.cpp-woa-vulkan).
- **Bandwidth-bound evidence on integrated AMD**: Strix Halo MoE decode at ~149 GB/s effective = ~58% of the 256 GB/s peak with Vulkan (issue #24438) — i.e., kernels still leave headroom but bandwidth is the wall; a 3B-active model at 2.5-bit (~0.94 GB/token) on ~290 GB/s effective bounds tg at ~300 t/s before overheads.

### Inferences
- On gfx1013 (no coopmat, probably no DP4A) 1-bit/ternary matvec gains must come from *reduced bytes moved*, not int-dot compute — so sub-2-bit expert quants raise the bandwidth ceiling directly, while dequant ALU stays hidden under memory latency (RDNA1's wide scalar issue of LUT dequant is "free" at 1 decode token/step).
- RDNA2 (gfx1030, if PS5 is 10.3): DP4A exists; only FA-KV uses it upstream. A DP4A GEMV for a packed int8/int4 expert format on gfx1030 is an unclaimed, plausible win (the hanzo 196 GB/s datapoint is the existence proof on newer silicon).
- #27952's existence implies CPU-side quantized-GEMM-style tricks could port to Vulkan MMV later, but nothing ships for RDNA1/2 today.

### Gaps
- No RDNA1-vs-RDNA2 side-by-side IQ2_XS/IQ1_S/IQ2_S Vulkan decode benchmark found anywhere in 2025–2026 sources.
- No measured dequant-bound vs bandwidth-bound crossover curve for ggml-vulkan; closest proxies are the #24438 effective-BW table and the #28226 IQ4_XS parity note.
- Whether gfx1013 (Cyan Skillfish "RDNA 1.5", gfx1013 is the Navi 10-family die used in PS5/BC-250) exposes `dotProduct` in Vulkan: not found; akandr notes it behaves "like a GFX10.1-era variant" with RDNA2-like RT extensions ("RDNA 1.5" is informal) — [akandr/bc250](https://github.com/akandr/bc250/blob/main/Readme.md).

## Q3. CPU-side expert compute on UMA (ktransformers-style) — does it fit PS5?

### Takeaway
ktransformers' CPU-expert story is built on AMX/AVX-512 server CPUs; the PS5's Zen2 has AVX2/FMA only (no AVX-512, no AMX), and — decisive — on the PS5 the CPU's "RAM" is the *same* GDDR6 pool the GPU streams from, so CPU experts buy no extra bandwidth, only extra latency and sync cost. Upstream evidence (issue #26876 on an Intel iGPU UMA, BlobPager's dead valley) says hybrid CPU/GPU expert splits on UMA underperform both pure modes unless the split is heavily skewed GPU-side.

### Cited findings
- **KTransformers (SOSP'25 paper)**: Arithmetic-Intensity-aware hybrid kernel, AMX-specialized CPU MoE kernels (1.69–4.30x microbenchmark speedups), async CPU-GPU scheduling via CUDA Graphs, +1.83x prefill from dynamic scheduling; balanced config = 5 immediate + 3 deferred experts/layer; deferring 4 experts gave no more throughput due to CPU saturation — [SOSP25 paper PDF](https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/SOSP25-chen.pdf). AMD support: ROCm on AMD GPUs since Mar 2025; kt-kernel has AVX512-FP8/BF16/INT4 and AMX INT4/INT8 backends plus an AVX2/AVX512 llamafile-based universal CPU backend; "AVX512 x86 CPUs including AMD servers, without AMX" for LoRA — [README](https://github.com/kvcache-ai/ktransformers/blob/main/README.md), [kt-kernel README](https://github.com/kvcache-ai/ktransformers/blob/main/kt-kernel/README.md). Server-class results: DeepSeek-V3.2-class decode 10.6–27.6 t/s on 1×RTX 5090 + dual-EPYC/dual-Xeon configs — [ktransformers benchmarks](https://ktransformers.net/en/benchmarks).
- **Zen2 capability**: PS5 CPU = 8c/16t Zen2 @3.5 GHz, AVX2/FMA/F16C/BMI2, **no AVX-512** — [PS5LM RESEARCH.md](https://github.com/cobanov/PS5LM/blob/main/docs/RESEARCH.md).
- **AMX-class off-the-table datapoint**: cecil-the-coder's Strix Halo streaming study lists "Intel AMX (28 t/s per KTransformers)" as a hardware upgrade path vs their 14 t/s GPU-streaming PoC, and rejected CPU expert compute because "**Vulkan matmul is ~10x faster than CPU GEMV for the expert projection sizes**" — [design.md](https://github.com/cecil-the-coder/llama-cpp-moe-flash/blob/main/docs/design.md).
- **CPU-experts measured in llama.cpp**: BlobPager `--cpu-moe 12` → 50.31 t/s vs `--cpu-moe 48` → 25.23 t/s on a dGPU box; per-expert-draw CPU cost ~145 µs; **partial offload on an integrated GPU (Intel Arc 140T iGPU, Arrow Lake-H, UMA) produces throughput BELOW both pure-Vulkan and pure-CPU** — [discussion #29234](https://github.com/ggml-org/llama.cpp/discussions/29234), [issue #26876](https://github.com/ggml-org/llama.cpp/issues/26876).
- **AMD NPU hybrid precedent (not CPU-matvec)**: AMD's GPT-OSS-20B on Ryzen AI NPUs does routing on CPU + batched expert GEMMs on NPU (INT4), 10.9–12.6 t/s — orchestration pattern is relevant, compute is NPU not AVX2 — [AMD technical article](https://www.amd.com/en/developer/resources/technical-articles/2026/accelerating-gpt-oss-20b-on-amd-ryzen-ai-npus.html).

### Inferences
- Zen2 AVX2 GEMV for expert FFNs is ~10x slower than the GPU's own matvec per cecil's design note, and BlobPager's 145 µs/expert-draw CPU cost at ~7 GB/s-class DDR would sink a 2230-MHz-36-CU GPU decode loop running at single-ms steps. CPU experts on PS5 make sense only as BlobPager-style *miss correction* (rare layers), never as a steady-state path.
- Because the PS5 memory pool is shared, the only scarce resource is *bytes moved per token*, not addressable capacity beyond 16 GB; ktransformers' core premise (cheap DRAM capacity + bandwidth) doesn't hold. The 15 GB-usable/12 GiB-direct constraints (Q6) reinforce GPU-resident experts as default.
- PS5-side CPU cost is also power/thermal: the shared power envelope means AVX2 GEMV on 8 cores steals clocks from the GPU (ps5 boost is an envelope game — [ps5-linux-power](https://github.com/bizkut/ps5-linux-power/blob/main/docs/TECHNICAL.md)).

### Gaps
- No published Zen2 (or any AM4/AM5 consumer) AVX2 MoE-expert GEMV tok/s figure found; nearest is cecil's "~10x slower than GPU" design-note estimate and PS5LM's payload CPU-mode observation of **~1 token/minute** for disk-mapped IQ1_S 27B on PS5 (mmap paging-bound, not pure GEMV) — [PR #12](https://github.com/cobanov/PS5LM/pull/12).
- No Strix Halo CPU+GPU hybrid-MoE ktransformers thread with numbers was found in these searches (agledger guide not reached).

## Q4. Overlap/pipelining on x86 UMA; spec-decode status on Vulkan

### Takeaway
The CUDA-style overlap playbook translates badly to ggml-vulkan: a second backend instance shares the one Vulkan device queue, so expert-prefetch streams *regress* on Vulkan; the wins instead come from pinning host buffers (`GGML_VK_REGISTER_HOST`), host-pointer import, and — for SSD streaming — io_uring pre-staging into double-buffered slabs during the attention window. On spec decode: MTP is merged upstream with Vulkan kernels, pays ~1.5x on RDNA3.5 Vulkan in a tuned fork, but the BC-250/gfx1013 verdict of "no wall-clock gain" stands in the fork README (as of its Apr 2026 snapshot), and a Vulkan+MTP multi-slot perf bug (#27544) was still open in Oct 2026.

### Cited findings
- **`GGML_SCHED_PREFETCH_EXPERTS=1` (expert prefetch on second stream): CUDA only — "on the Vulkan backend the second backend instance shares one device queue, giving no overlap, so this regresses."** Pinning (`GGML_CUDA_REGISTER_HOST`, honored as `GGML_VK_REGISTER_HOST`) works on Vulkan too: H2D uploads ~6–7→~20 GB/s by avoiding the driver bounce buffer; on RX 580 Vulkan "pinning is the win" — [Lumpiasty llama.cpp docs commit](https://gitea.lumpiasty.xyz/Lumpiasty/llama.cpp/commit/891760faba3d1f5f4486d57dc2522e6b13a53ffd)
- **VK_EXT_external_memory_host in llama.cpp**: merged PR #18467 (`buffer_from_host_ptr` + host-buffer registration/pinning path) — [commit mirror](https://gitea.lumpiasty.xyz/Lumpiasty/llama.cpp/commit/ea13cba85092fa17cae4d7bd064e5476a86ea53c), [pinning commit](https://gitea.lumpiasty.xyz/Lumpiasty/llama.cpp/commit/8a545c7820d8e37a195cd8a19bd93d9d31ffdbf5). Caveat from the same fork's changelog: "**VK_EXT_external_memory_host import fails on RADV for file-backed mmap pages**" → uploads fell to ~3 GB/s pageable memcpy; fix = one-time copy into a host-visible pinned buffer — [changelog](https://gitea.lumpiasty.xyz/Lumpiasty/llama.cpp/commits/commit/891760faba3d1f5f4486d57dc2522e6b13a53ffd). Feature request to bypass staging when dst is host-visible (#21590) closed as not planned — [issue #21590](https://github.com/ggml-org/llama.cpp/issues/21590).
- **Double-buffered expert slabs + io_uring**: cecil's design streams K experts for layer N during layer N−1's attention window; 8×5.9 MB at 7 GB/s ÷ 4-deep queue ≈ 1.7 ms vs 1.75 ms attention window; warm page cache makes it 0.4 ms; staging pool ~208 MB — [design.md](https://github.com/cecil-the-coder/llama-cpp-moe-flash/blob/main/docs/design.md). Academic version (ProMoE, integrated into llama.cpp): predictive expert prefetch off the critical path, 23 GB/s PCIe ceiling — [arxiv 2410.22134](https://arxiv.org/html/2410.22134v1).
- **RPC pipeline parallelism (PR #18626) enabled the first 122B MoE on BC-250 hardware**: 4 nodes × Qwen3.5-122B-A10B IQ3_S, gen 29.5 t/s at 28k ctx; but **pipeline parallelism silently switches off when MoE weights sit in host RAM** (llama-context `!has_tensor_overrides()` check from #11397) — [discussion #28226](https://github.com/ggml-org/llama.cpp/discussions/28226), [discussion #29964](https://github.com/ggml-org/llama.cpp/discussions/29964).
- **Spec decode on Vulkan, 2026 status**: MTP support merged (`--spec-type draft-mtp`, PR #22673, May 2026) incl. "vulkan: add GDN partial rollback" for MTP rollback of recurrent state — [commit mirror](https://gitea.gnumetry.com/ggml-org/llama.cpp/src/commit/255582687b8dd211fdbc582e43ab842491554e94/ggml/src/ggml-vulkan). EAGLE3 draft type exists (`draft-eagle3`) — [llama-speculative manpage](https://manpages.debian.org/testing/llama.cpp-examples/llama-speculative.1.en.html). **Open issue #27544: "spec + vulkan: Performance Drop with MTP n-max > 1 and -np > 1"** (mentioned Oct 6, 2026) — [PR #27332 mentions](https://github.com/ggml-org/llama.cpp/pull/27332). On BC-250/Vulkan: "**Speculative decoding: doesn't deliver on BC-250 (Vulkan)** — we could not measure a speedup" (TechMakesArt fork README, consistent with the Sept 2026 community note; fork is an Apr 2026 snapshot, not retested on b10727+ in that source) — [llama.cpp-bc250](https://github.com/TechMakesArt/llama.cpp-bc250). Counterpoint on newer silicon: Strix Halo fork achieves **~1.5x decode with MTP on Vulkan** with the draft running sparse; DFlash2 merged as PR #27342 and RDNA4 guides report MTP ~2 tok/step on 27B dense (b10820) — [discussion #30282](https://github.com/ggml-org/llama.cpp/discussions/30282), [RDNA4 guide](https://github.com/aguaishuo/AMD-Radeon-AI-PRO-R9700-llama-cpp-Vulkan-MTP). MoE MTP on CUDA: 98→144 t/s on 16 GB GPU; dense 42% *slower* (verify path is bandwidth-bound) — [njannasch.dev](https://njannasch.dev/snippets/llama-cpp-mtp-server-qwen/).
- **Graph/plan caching**: Strix Halo fork added a graph/allocation-plan cache (big dispatch-overhead win at 1M ctx) — [discussion #30282](https://github.com/ggml-org/llama.cpp/discussions/30282). No merged CUDA-graphs-analog (Vulkan command-buffer replay) in upstream ggml-vulkan found.

### Inferences
- For a streamed-MoE engine on PS5: overlap must be *manual* — pread/io_uring into pinned host slabs during the GPU attention window, patched slot-maps into mul_mat_id push constants (cecil's MUL_MAT_ID_STREAMING design), because the naive two-queue trick is known to regress on Vulkan. On UMA the "H2D copy" is just a memcpy inside the same GDDR — a copy-engine-free RDNA1/2 APU will spend SMs on it unless the shader reads the host slab directly via an imported host pointer (external_memory_host works for malloc'd, not file-backed, pages on RADV).
- MTP on gfx1013 remains "fixed-then-retest": #27332's density gate (+36% at B=9) attacks exactly the batched-verify matmul cliff that killed spec decode there, and #27544 shows the multi-slot MTP cliff persists; a PS5 A/B of MTP n-max=1 with the density gate backported is the cheap, high-value experiment.
- RPC pipeline parallelism turning off with host-resident experts is a trap for any "experts in GTT, rest on GPU" design: it serializes; a single node (PS5) avoids this, but any dual-PS5 RPC plan must keep experts out of tensor-overrides.

### Gaps
- No measured Vulkan async-prefill numbers on gfx10 (upstream async prefill/overlap work not located); the RPC #18626 gains are cluster-level.
- Whether MTP was ever retested on BC-250/PS5 with b10727+ builds: no source found.

## Q5. GPU-side weight/traffic tricks: partial offload, KV quant, L2/clock knobs

### Takeaway
Two measured, PS5-relevant traffic tricks stand out: forcing the NVIDIA-gated `shmem_staging` FA path on gfx1013 (+12–50% depth-dependent prefill; +55–68% cluster-wide) and quantized KV only when depth actually costs bandwidth. Resident-shared-experts-plus-streamed-routed is validated by BlobPager's slot-pool geometry, not by `-ncmoe` partial offload (which has a dead valley). Clock levers are real on PS5: `ps5_control --boost` (GPU 2230 MHz), and a userspace tool can set GPU GFXCLK 400–2380 MHz and DF/memory P-states; no gfx10 RADV L2-residency API found.

### Cited findings
- **shmem_staging FA on gfx1013**: the NVIDIA-gated FA path from PR #19625, force-enabled, gave a 4-node Qwen3.5-122B cluster prefill 96→162 t/s (+68%) and gen 19.0→29.5 t/s (+55%); single-node A/B on gemma-4-26B MoE IQ3_S: **+12% pp at d0, +34% at d4096, +50% at d8192** (issue #25207) — [discussion #28226](https://github.com/ggml-org/llama.cpp/discussions/28226).
- **Partial offload geometry**: BlobPager E6 — naive splits into a dead valley (32–40 CPU layers → 15.7–17.3 t/s) while `--cpu-moe 12` (≈12/47 layers CPU-routed-experts, rest GPU, i.e. resident shared+dense on GPU) hits 50.31 t/s — [discussion #29234](https://github.com/ggml-org/llama.cpp/discussions/29234). DocShotgun's MoE guide: `-ngl 999 -ot "exps=CPU"` + `--n-cpu-moe` fills spare VRAM with routed-expert layers from one end — [gist](https://gist.github.com/DocShotgun/a02a4c0c0a57e43ff4f038b46ca66ae0).
- **KV quantization**: mixed results. On RX 580-class Vulkan, `-ctk/-ctv q8_0` is *slower* — "dequant overhead in the scalar FA kernel outweighs the bandwidth saving"; on modern setups q4_0 KV is standard for fitting 64k on 16 GB (MTP server configs), and PS5LM runs Q2_K_XL 27B at 32k with q4_0 cache at 20.3 t/s — [Lumpiasty docs](https://gitea.lumpiasty.xyz/Lumpiasty/llama.cpp/commit/891760faba3d1f5f4486d57dc2522e6b13a53ffd), [njannasch.dev](https://njannasch.dev/snippets/llama-cpp-mtp-server-qwen/), [PS5LM PR #12](https://github.com/cobanov/PS5LM/pull/12). Upstream DP4A FA (#20797) directly attacks the q8_0/q4_0-KV dequant cost on DP4A-capable GPUs (i.e., gfx1030 yes / gfx1013 likely).
- **GPU clock (PS5)**: `ps5-linux-tools/ps5_control --boost on` (+`--fan on`) raises GPU to 2230 MHz and CPU to 3500 MHz via /dev/icc and /dev/mp1 mailboxes — [ps5-linux-tools](https://github.com/ps5-linux/ps5-linux-tools), [ps5-linux-loader README](https://github.com/ps5-linux/ps5-linux-loader). `bizkut/ps5-linux-power` exposes `ps5_gpu set <MHz> force` (accepted range **400–2380 MHz**) and **DF/memory fabric P-state** read/write tools; "GPU clock changes are usually the largest power lever" — [TECHNICAL.md](https://github.com/bizkut/ps5-linux-power/blob/main/docs/TECHNICAL.md). This is the closest PS5 analog to a pp_table/softPowerPlay edit; memory-clock values settable this way are not published (**gap**).
- **CU unlock**: ps5-linux kernel patch unlocks harvested CUs via `amdgpu.ps5_cu_unlock=N`; benchmark table: PS5 36 CU @~2200 MHz = 5040 pts vs BC-250 36 CU = 5330, BC-250 40 CU = 5290–5530 (a "40 CU + boost" PS5 row scored 5041 with GPU reported at 3493 MHz "actual" — flagged black-screen/uncertain) — [ps5-linux guide GPU page](https://rmuxnet.github.io/ps5-linux-guide/guide/gpu). Confirms 36 CU ceiling for PS5 (matches task premise; 40-CU is BC-250 territory, cf. [duggasco/bc250-40cu-unlock](https://github.com/ggml-org/llama.cpp/discussions/28226) credit in #28226).
- **Governor**: BC-250 community governor work (cyan-skillfish-governor, filippor) credited as "the biggest single win" in the 5×BC-250 cluster — [discussion #28226](https://github.com/ggml-org/llama.cpp/discussions/28226). PS5 analog = ps5boost.service at boot.
- **RADV knobs**: `RADV_DEBUG=nocompute` worth +15% on RDNA4 (27B pp 120→138 t/s); gfx10-relevant RADV compute tuning for gfx1013/1030 not found — [RDNA4 guide](https://github.com/aguaishuo/AMD-Radeon-AI-PRO-R9700-llama-cpp-Vulkan-MTP). No L2-residency/persistence or VK_EXT_host_image_copy usage in ggml-vulkan found (**gap**).

### Inferences
- The shmem_staging finding is portable to PS5 under pLinux5 (it's a Mesa/ggml flag, not NVIDIA hardware) and would specifically rescue deep-context streamed decode where FA traffic grows; on the native-OS PS5_Mesa port the same shader exists (Mesa 26.2-based RADV — Q7), gated the same way.
- On a 36-CU APU at 290 GB/s effective, a 3B-active 2.5-bit expert model moves ~1 GB/token → GPU-side traffic tricks (KV q8/q4 at depth, FA path efficiency) are worth 10–50% at long depth but ~0 at short context; the resident-pool geometry matters more.
- DF/memory P-states being mailbox-addressable means a max-memory-P-state lock (kill the memory downclock between tokens) is plausible on pLinux5 without touching BIOS — worth testing `ps5_gpu`/DF tools against idle-GPU power caps.

### Gaps
- No gfx10 RADV L2-persistence (VK_EXT_image_compression/residency) evidence; no rasterization-order knobs found for compute on gfx10.
- Whether PS5 GDDR (14 GB/s modules, 448 GB/s peak) has an accessible higher P-state via /dev/mp1 — unverified.

## Q6. GPU memory budget maximization for resident weights on 16 GB UMA

### Takeaway
Under pLinux5 the practical GPU-visible budget on PS5 is GTT-tunable up to roughly the whole 16 GB minus OS (~15 GB usable reported), via `amdgpu.gttsize`; llama.cpp needs `GGML_VK_FORCE_MAX_ALLOCATION_SIZE` tweaks on these APUs. On the native OS, PS5LM's title path gets a **12 GiB direct-memory device heap** (`radv_enable_unified_heap_on_apu` → one 11.44 GiB Vulkan heap). The page-cache double-copy problem is real on UMA and has two measured mitigations: LOAD_MODE=dio (O_DIRECT-style load) and the fact that RADV cannot import file-backed mmap pages via external_memory_host — a one-time copy into a host-visible pinned buffer is the sanctioned fallback.

### Cited findings
- **GTT**: BC-250 guides tune `amdgpu.gttsize=14336` (14 GiB) kernel arg — [akandr/bc250](https://github.com/akandr/bc250/blob/main/Readme.md). Digital Foundry's PS5 Linux test: "**Around 15 GB of useable memory**" under Linux — [Digital Foundry](https://www.digitalfoundry.net/news/2026/05/playstation-5-linux-tested-steam-pc-vs-native-ps5-games).
- **llama.cpp allocation quirks on this APU class**: bc-250.com wiki: llama.cpp assumes 8 GB system RAM → OOM without `-cram`-style limits; `GGML_VK_FORCE_MAX_ALLOCATION_SIZE=2000000000` (2 GB chunks) recommended — [bc-250.com AI wiki](https://bc-250.com/wiki?article=linux/12-ai-inference). UMA heap mis-detection on Ryzen Max fixed by PR #17110 (b7020-era) — [issue #16832](https://github.com/ggml-org/llama.cpp/issues/16832). `GGML_VK_DISABLE_HOST_VISIBLE_VIDMEM` toggles the shared/dedicated preference — [issue #12748](https://github.com/ggml-org/llama.cpp/issues/12748).
- **external_memory_host on RADV**: works for malloc'd host pages (PR #18467 + GGML_VK_REGISTER_HOST pinning) but **fails for file-backed mmap pages**, making mmap'd expert uploads pageable-memcpy-bound (~3 GB/s); sanctioned workaround = one-time copy into host-visible pinned buffer (costs host-visible bytes equal to the CPU-resident region) — [Lumpiasty changelog](https://gitea.lumpiasty.xyz/Lumpiasty/llama.cpp/commits/commit/891760faba3d1f5f4486d57dc2522e6b13a53ffd).
- **Page-cache pressure mitigations**: PR #27928 proposes disabling mmap prefetch (avoid reading all weights at startup then having the OS page them out) — [PR #27928](https://github.com/ggml-org/llama.cpp/pull/27928); production BC-250 cluster uses `LLAMA_ARG_LOAD_MODE=dio` — [discussion #28226](https://github.com/ggml-org/llama.cpp/discussions/28226). O_DIRECT-style loading keeps expert bytes out of the RAM/GTT-shared page cache — on UMA, page-cache pages *are* stolen from the GPU's usable pool (same physical GDDR), which is exactly why the dIO path matters.
- **Native-OS budget**: a PS5 title sees flexible memory of only ~190–448 MiB; large data goes in **direct memory**; PS5SX2's ps5vk fork offers a 12 GiB device heap via PS5VK_WIDE_MEMORY, and ProsperoAI maps ~7.38 GiB in one block — [PS5LM RESEARCH.md](https://github.com/cobanov/PS5LM/blob/main/docs/RESEARCH.md). PS5LM app with `radv_enable_unified_heap_on_apu=1`: **one 11.44 GiB device heap; default is 2/3 of the pool** — [PS5LM PR #12](https://github.com/cobanov/PS5LM/pull/12).
- A feature request to run MoE experts from host RAM by PCIe DMA with no H2D copy (23 GB MoE on 1.6 GB VRAM) is open as #26448 — on UMA that model degenerates to "no copy needed," but it validates the resident-pool+slot-indirection design — [issue #26448](https://github.com/ggml-org/llama.cpp/issues/26448).

### Inferences
- Realistic resident budget on pLinux5 PS5: ~13–14 GiB weights+KV for llama.cpp after OS/page-table/compute-buffer overhead (bc-250 experience on identical memory: ~14 GiB practical with GTT tuning, minus Linux overheads); native OS: 11.44 GiB heap, one process, no GTT knob at all. A streamed model must therefore fit non-experts+KV in ~10 GiB and stream only the routed-expert delta.
- The UMA page-cache trap is asymmetric: streamed reads via buffered IO inflate page cache that competes with GPU allocations *and* steal GDDR bandwidth on copy; dIO+direct-to-pinned-pointer (or BlobPager-style pread) is the only clean pattern — buffering expert reads *does* steal from the GPU's usable budget.
- On native OS, sceKernelMapDirectMemory pages (physically contiguous, 2 MiB) could serve as the streaming slab and be handed to RADV as its own device heap's memory — likely *cheaper* than Linux GTT (no second copy), untested (**gap**).

### Gaps
- No measured llama.cpp-on-ps5-linux GTT ceiling experiment found (BC-250 numbers are the proxy).
- No published page-cache-vs-GPU-budget measurement on Oberon APUs.

## Q7. PS5_Vulkan / native-OS path (PS5LM, abhi245y fork)

### Takeaway
The native-OS path is real and already runs llama.cpp+ggml-vulkan on PS5's GPU: cobanov/PS5LM (payload, ~1.6 GB model cap) and abhi245y's PS5LM Plus (native title, 12 GiB direct memory, RADV from a Mesa 26.2 fork over Sony AGC) run Qwen3.8-27B quants at 20–21 t/s on the console — with everything resident, no streaming yet. A CPU-only *disk-mapped* payload mode existed and crawled at ~1 token/min, which is the baseline expert streaming must beat under the native OS, where the FreeBSD-derived kernel's page cache is the only IO mechanism.

### Cited findings
- **cobanov/PS5LM** (created Oct 1, 2026): llama.cpp on jailbroken PS5; v0.1 payload opens a model library in the PS5 browser; payload can lock only **~1.6 GB** of model without starving the home screen; Qwen3.5 0.8B 13–21 t/s, 2B ~9 t/s (CPU); **UD-IQ1_S mapped from disk on CPU ≈ 1 token/minute** — [repo](https://github.com/cobanov/PS5LM).
- **abhi245y "PS5LM Plus" native GPU app (PR #12, merged 2026-10-13)**: native title (PPSA99581, ShadowMountPlus) links llama-server + ggml-vulkan against **PS5_Vulkan's RADV build** (Mihawk-99's PS5_Vulkan + PS5_Mesa [Mesa 26.2 fork, PS5 winsys over AGC] + PS5_PayloadSDK); **Vulkan 1.4, ACO shader compile on-console**. Results (PS5 13.x): Qwen3.8-27B UD-IQ2_XXS 6.77 GiB @64k: **20.7 t/s**; UD-Q2_K_XL 9.15 GiB @32k q4_0-KV: 20.3 t/s (7,775-token answer at 19.7); Gemma 4 E4B q4_0 from USB: 61 t/s; Llama 3.2 3B: 124 t/s. Title gets **12 GiB direct memory**; `radv_enable_unified_heap_on_apu` → one **11.44 GiB device heap** (default 2/3 pool); models load fully into GPU memory from USB (`-lm none`) — [PR #12](https://github.com/cobanov/PS5LM/pull/12), [abhi245y/PS5LM](https://github.com/abhi245y/PS5LM).
- **Platform facts** (RESEARCH.md): Zen2 8c/16T ≤3.5 GHz, AVX2/FMA/F16C/BMI2, no AVX-512; 16 GB GDDR6 **448 GB/s peak** (Pro: 576); GPU "RDNA 2 class, programmed through Sony's private AGC interface", no public compute API; FreeBSD-derivative OS; big allocations via sceKernelAllocateDirectMemory/sceKernelMapDirectMemory (2 MiB, type 12, RW both sides); flexible pool ~448 MiB; leans on PS5SX2/ProsperoAI/PS5_Vulkan memory notes — [RESEARCH.md](https://github.com/cobanov/PS5LM/blob/main/docs/RESEARCH.md).
- **Upstreaming**: PS5 Linux work is seeding mainline — Mesa 26.1-devel added PS5 GPU support and an amdgpu DCN fix landed after Andy Nguyen's ps5-linux — [VideoCardz](https://videocardz.com/newz/ps5-linux-hack-leads-to-first-mesa-update-for-sony-gpu); ps5-linux kernel patches add CU unlock and SMU frequency reporting — [ps5-linux-patches](https://github.com/ps5-linux/ps5-linux-patches).
- PS5LM Plus dashboard exposes memory-pool split (model/KV/rest) from llama-server /metrics + direct-memory kernel figures — useful instrumentation hook for an engine — [PR #12](https://github.com/cobanov/PS5LM/pull/12).

### Inferences
- Expert streaming under the **native OS** is feasible exactly along the PS5LM Plus seams: (a) the 12 GiB direct-memory slab doubles as a GPU-resident expert pool + host-visible staging ring since direct memory is CPU+GPU RW at page level — this is the native analog of VK_EXT_external_memory_host with zero copy; (b) the PS5-OS page cache (FreeBSD) can serve streamed reads, but the 1 tok/min IQ1_S disk-mapped payload result shows demand-paging a GGUF is unusable without a purpose-built readahead/producer thread pinned into direct memory; (c) models can also live on USB (FAT/NTFS via app) — the app already streams whole files, so chunked reads need no new syscall surface.
- The 20.7 t/s 27B dense decode on the *native* driver implies the PS5_Vulkan RADV port is not the bottleneck for ggml compute on this silicon — a streamed-MoE build (e.g., a Qwen3-30B-class A3B at ~1.5 GiB active bytes/token) should approach the ~290 GB/s roofline on either OS; native path has less OS memory overhead (11.44 GiB heap + page tables) but no O_DIRECT, no GTT knob, and no ps5_control boost (GPU clocks under native OS are AGC-managed).
- pLinux5 remains the faster-to-bring-up path (standard Mesa, GTT tuning, boost/fan tools, DIO load mode all exist); native path buys back ~1–2 GiB of budget and console-as-product ergonomics.

### Gaps
- PS5_Vulkan's external_memory_host/dedicated-allocation support on the native heap is undocumented in sources found.
- No PS5LM report of MoE models yet (only dense 27B/4B/3B) — MoE mul_mat_id behavior on PS5_Vulkan RADV is unmeasured.
- No PS5LM/spec decode (MTP) or SSD-class (NVMe vs USB) streaming benchmarks under the native OS.

## Cross-cutting PS5-adaptation summary (for the report writer)
- Highest-confidence, on-target numbers: fused gate/up glu kernel +48.6% tg on gfx1013 (Q1); density gate +36% at B=9 (Q1); shmem_staging FA +55% gen/+68% pp at 122B scale (Q5); dIO load mode in production on identical silicon (Q6); PS5LM 20.7 t/s 27B native-GPU ceiling (Q7).
- Do-not-use list with evidence: second-stream expert prefetch on Vulkan (regresses — queue sharing, Q4); CPU-side experts as steady state on UMA (Q3: #26876, dead valley, ~10x GEMV gap); naive 50/50 `-ncmoe` splits on UMA (Q1/Q5); buffered-mmap expert paging (Q3/Q6: ~1 tok/min, page-cache eviction + no RADV mmap import).
- Unresolved silicon question: gfx1013 vs gfx1030 changes the answer to DP4A (Q2) and possibly FA path choice — a 5-line vulkaninfo check on the target is the cheapest de-risking step; akandr's "GFX10.1-era ISA, RDNA2-ish RT" note ([bc250](https://github.com/akandr/bc250/blob/main/Readme.md)) suggests gfx1013 = RDNA1 compute ISA (no v_dot4).
