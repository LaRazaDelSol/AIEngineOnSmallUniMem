## 0. Direct answers to the three questions

**Q1 — Can it be an app on the homescreen that takes over the machine — "all 16 GB minus what the OS needs" — until you exit, without anything risky?**
Yes. The safe ceiling is Sony's own game budget, not a hack:

| Mode | Memory you get | What the OS keeps | Risk |
|---|---|---|---|
| Payload (elfldr process) | ~6.25 GiB of an 8 GiB shared flexible pool; 5 cores | everything running | none, but crippled — **not** the product mode |
| **Native title (game context)** | **12 GiB direct memory → 11.44 GiB one-heap RADV device heap** ([measured](https://github.com/cobanov/PS5LM/blob/main/docs/CONSOLE.md)); DF: games get "an actual 12.5 GB of useable memory" | ~3.5 GB (kernel, hypervisor, minimal services) | **zero** — identical to what every commercial game does; dashboard suspends while running, resumes on close |
| pLinux5-NG boot | **~15 GB to userspace** (DF), all 8c/16t, boost via `ps5_control` | ~1 GB (kernel + GPU stack) | low — same JB, different boot target; nothing persistent, nothing written to flash (M.2 partition excepted) |

16.0 GB is not reachable in any mode: the hypervisor + kernel are permanently resident — that *is* "what the OS needs" (the base PS5's HV maps its own region at PA `0x062800000`). What you *can* reclaim is the ~2–4 GB of system software (dashboard, apps, system caches) — and title mode already reclaims exactly that by suspending the dashboard. Pushing a title's 12 GiB budget higher needs an undocumented kernel memory-budget patch — that's where "breaking" starts, so the plan keeps it out.
Homescreen entry: **ShadowMountPlus directory title** (`/data/homebrew/<TITLEID>/` → real Games-row tile with icon; what PS5LM `PPSA99575` and Wings `PPSA99178` ship today). PKG install works too (early Byepervisor-Reborn test builds, 13 Oct) but is experimental. Engine hygiene for max reclaim: UI kept tiny (ps5-homebrew-ui costs ~0.35 GiB), never `exit()` (shell closes / `LoadExec` restart), close-background via the tile's own lifecycle.

**Q2 — Can we use the specialized chips?**
Mostly yes, with one big "no NPU":
- **GPU (36 CU RDNA2, "GFX10.3", reports as RADV NAVI21, Vulkan 1.4 via mihawk-99's PS5_Vulkan RADV port):** yes, proven — ggml-vulkan runs on it (PS5LM: Qwen3.5-9B 55 tok/s, Qwen3.8-27B ~20 tok/s). No cooperative-matrix, no accelerated int-dot on RADV → fp16 shader matmuls (verified in PS5LM RESEARCH; matches "int8 coopmat is RDNA3/4-gated"). GDDR6 peak 448 GB/s (Pro: 576).
- **SSD subsystem (the star for this project):** internal Gen4 x4 (~5.5 GB/s class) + optional M.2 (Gen4 x4, 6.5–6.6 measured in-bay). Both enumerate under ps5-linux (`/dev/nvme0` + `/dev/nvme1`); aggregate never measured = gate N6. Under PS5 OS you get filesystem speed on `/data`, not raw queues.
- **Kraken/hardware-decompression block:** real silicon, but **no driver in any ps5-linux artifact** and irrelevant anyway — Q4-class weights are near-max-entropy; a codec on them measured −13% (flash-moe). Kill the 9.9 GB/s myth (SEO source).
- **VCN (video codec):** works under Linux (VAAPI) — only useful if you add vision pre/post-processing.
- **No NPU.** No dedicated ML block on the standard PS5 (the PS5 Pro's ML/PSSR path is moot for this project. S5 correction 2026-10-21: Pro *Linux* support is back upstream — the live loader README lists **PS5 Pro 13.60 with M.2** (DeathlySin, E820/I-O fixes) — but only at 13.60, so it stays irrelevant to a 13.00-freeze Phat).
- **VCN/USB/GbE/DualSense:** peripheral tier (~0.9 GB/s per USB 3.1 Gen2 port, 1 GbE ≈ 110 MB/s, FTP measured 61 MB/s).

**Q3 — The "entry app": an OpenCode-like setup where an agent on another server sees the PS5 and interacts with it directly. Does it exist?**
**Yes — it exists: [`leolobato/ps5-mcp`](https://github.com/leolobato/ps5-mcp) (MIT).** "See and control a jailbroken PS5 from an MCP agent, with live HDMI video and audio." Verified feature set:
- **See:** live HDMI video+audio into the agent's machine via a USB capture card (HDCP off on the PS5); `snapshot`, MP4 record, MJPEG browser stream; `wait_for` / template matching for visual automation.
- **Touch:** a `padd` payload on the console creates a **virtual DualSense** over TCP :9305 — press/hold/stick/trigger/sequence, `home`, close app, launch by title-id; games only accept the controller that launched them, so it launches via `launch` and steers that pad.
- **Do:** install `.pkg` / register homebrew titles (integrates ShadowMountPlus's :10101 API to verify registration), `push`/`pull` files (zftpd :2120), payload Start/Stop through Payload Manager :8084, app list via Web File Manager :8888, key-recording replay, `claim_console`/`release_console` so multiple agents share one console safely.
- **Agent hookup:** standard MCP server (`ps5mcp-server`), with copy-paste configs for common coding agents — i.e., a coding agent on the PC uses the PS5 as a real, visible, clickable machine.
Limits to know: the reference app is **macOS-only for now (Windows planned — you're on Windows; the Python server + ffmpeg capture fallback exist, and a Windows port is a bounded contribution)**; tested on 13.60 — your 13.00 uses the same payload stack, so it should work but counts as a first-party test; needs capture-card hardware (~$20 USB HDMI dongle is enough for 1080p60 viewing, low-latency cards better for automation).

So **don't port OpenCode to the console** and don't build a bespoke entry app. The two existing halves already compose the architecture:
1. **ps5-mcp** = agent's *eyes and hands* on the console (screen + pad + files + install), from your server.
2. **PS5LM's :8081 API** (OpenAI/Responses/Anthropic; common coding agents verified against it) = the console's *model* exposed to the same agents.
The engine project adds the third half — the streaming inference layer — and the only genuinely new entry-app work left is optional polish: ship the PS5-MCP host-side pieces you need natively (a small titles-side status surface) and/or Windows support upstream.

### 2.5 Engine core (what we actually build)

### 2.9 Testing the Kraken decompression block without a driver
The unit sits in the I/O complex between flash and GDDR and is invoked **transparently** by the OS on reads of data stored with Oodle schemes (cbloom: "stored compressed on the SSD, decoded transparently at read"; HW implements the Oodle 2.2.0 feature set, LZ+Huffman). Under ps5-linux it is dead silicon — no driver, "storage treated as plain NVMe" (verified in every ps5-linux artifact). Escalation ladder, cheapest first:

1. **Linux-track existence probe (~30 min):** `lspci -nn -vvv` + `/sys/bus/pci/devices/*` census — log every Sony function block with an unbound BAR near the NVMe endpoints (that's the block inventory, for free). Then the decisive microbench: two identical 4 GiB files, one raw, one `zstd -19`/Kraken-compressible, `fio` seq-read both. **Pass = compressed read beats raw device line-rate** (it would prove a transparent HW path). Expected: no.
