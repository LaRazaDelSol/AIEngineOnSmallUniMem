# One PS5, One SSD, 100B+ MoE Streaming

> **Status (2026-10-21):** SUPERSEDED — cite-only. Replaced by the verified plan + the adversarial pass. Do not act on this.

**Verdict: build it, but gate hard on two measurements you can take in a weekend — M.2 read throughput under Linux and the firmware window — before writing any engine code.** The project is worth building because it fills an open gap (no single-PS5 100B+ MoE streaming result has been published as of Oct 2026), the silicon family is proven capable (a 5-board BC-250 cluster — the same "Cyan Skillfish" gfx1013 APU family — already serves Qwen3.5-122B-A10B at 29.5 tok/s), and two independent SSD-streaming engines (flash-moe, MoE-Direct) prove the pread + "trust the OS" page-cache approach works on unified-memory machines. The recommended approach is to reuse the proven flash-moe/MoE-Direct architecture rather than invent one, port it to a llama.cpp-Vulkan-on-RADV baseline (the path PS5LM already runs on the console), and de-risk the serial GPU→SSD→GPU dependency by measuring real M.2 throughput first — because that number is the single unknown that decides whether the whole build is viable. No console purchase is needed: the console is already on 13.x firmware, so the path is pLinux5-NG (13.20-confirmed, 13.60-experimental), not ps5-linux-loader. Confirm the loader boots on the existing console and the M.2 slot sustains ≥5 GB/s, then treat everything else as engineering, not research.

## What the research changed or confirmed

The research materially updates several premises in the build spec, and the biggest changes are all in the loader and memory-budget corner. **ps5-linux-loader is now maintained under the `ps5-linux` GitHub org (not the personal repo), supports Phat *and* Slim on firmware 3.00–7.61, and M.2-as-Linux-partition is gated to 4.xx–7.61 — 3.xx lacks M.2 because the PS5 fails to boot with it attached** ([Source](https://github.com/ps5-linux/ps5-linux-loader)). The spec's "3.xx–4.xx / Phat only" understanding is outdated. **TheFlow (Andy Nguyen) publicly abandoned the project on 15 Sep 2026** after the underlying hypervisor bug was reported to Sony, but the repos remain live and unarchived, so the loader is frozen-in-maintenance rather than dead ([Source](https://itsfoss.com/news/ps5-linux-lead-quits)). PS5 Pro support never reached the repo, so the console column is Phat + Slim confirmed, Pro abandoned. The high-firmware path, **pLinux5-NG, is explicitly "VERY work-in-progress": only 13.20 is confirmed booting, 13.60 is experimental, and 14.00/14.10 are blocked** (no public kernel exploit; the Reborn/Relapse bypass no longer works there) — and its README never mentions M.2, so M.2 behavior on high firmware is unconfirmed ([Source](https://github.com/pLabs5/pLinux5-NG)). Since the console is already on 13.x firmware, the firmware window is not an obstacle — the remaining question is whether pLinux5-NG boots on this specific 13.x (13.20 confirmed, 13.60 experimental) and whether M.2 works, which is a hardware test, not an acquisition gate.

**The M.2 throughput figure is still unmeasured — no published fio/hdparm/dd number exists under Linux on a PS5 as of Oct 2026.** The only datapoints are qualitative (Digital Foundry: "vastly accelerating storage speeds vs the USB alternative," no number; TheFlow's LBA-alignment fix with no before/after figures) plus PS5-OS-level reads of ~6.5–6.6 GB/s that are not Linux measurements ([Source](https://www.digitalfoundry.net/news/2026/05/playstation-5-linux-tested-steam-pc-vs-native-ps5-games), [Source](https://www.youtube.com/watch?v=fM1bJfnI2YU)). The spec's throughput premise must be flagged as unverified; the defensible statement is "Linux M.2 is qualitatively faster than USB, PS5-OS M.2 reads ~6.5–6.6 GB/s, no Linux figure published."

**The memory-budget picture is tighter than the spec assumes: the real working ceiling is ~13 GiB of model+KV, not 14.** Two independent kernel memory managers — the amdgpu GTT cap and the TTM page manager — each default to ~7.4 GiB (half of ~14.8 GiB system RAM), and the confirmed fix is to raise **both `ttm.pages_limit` *and* `ttm.page_pool_size`** to `4194304` (16 GiB), not just pages_limit ([Source](https://github.com/akandr/bc250)). There is a silent trap: **systemd-tmpfiles runs after boot and silently overwrites cmdline/modprobe values, capping GPU memory at 12 GiB — you must verify `/sys/module/ttm/parameters/pages_limit` reads `4194304` live** ([Source](https://github.com/akandr/bc250)). And akandr's own read is blunt: the *real* ceiling is ~13 GiB set by 16 GB physical RAM (weights + KV + compute + OS), not the software cap — a ~14 GiB model still won't run ([Source](https://github.com/akandr/bc250)). A streaming engine should budget ~13 GiB and treat 14.5–14.75 GB as the absolute driver ceiling.

**VK_EXT_external_memory_host is implemented by RADV** (gated on `has_userptr`), importing host pointers into the GTT-cached memory type — the right primitive for zero-copy SSD-to-GPU landing on UMA, since RADV reports the BC-250 as an INTEGRATED_GPU with two overlapping heaps (device-local 8.33 GiB + host-visible 8.17 GiB) that are views of the same 16 GB pool, not additive ([Source](https://lists.freedesktop.org/archives/mesa-dev/2018-February/184320.html), [Source](https://github.com/akandr/bc250)). Caveat: availability on gfx1013 specifically is *inferred* from RADV's general implementation, not directly measured — needs an on-target `vulkaninfo`/CTS check.

**The IQ4_XS penalty is a time-dependent build artifact, not a hardware limitation.** On the b8819 snapshot it was −23% on gfx1013 (no int-dot instructions), but by b10727 (Sep 2026) the cluster operator reports IQ4_XS is "speed-parity with Q4_K_S" — the old penalty is gone ([Source](https://github.com/TechMakesArt/llama.cpp-bc250), [Source](https://github.com/ggml-org/llama.cpp/discussions/28226)). A streaming engine must re-benchmark IQ4_XS on its own build rather than assume the old figure. Decode on gfx1013 is bandwidth-bound at ~290 GB/s (~65% of 448 GB/s peak), so quant choice is a quality-per-bit tradeoff, not a speed lever — Q4_K_M is the recommended default, IQ4_NL the size-alternative at near-parity ([Source](https://github.com/TechMakesArt/llama.cpp-bc250)).

**The SMU clock governor is the single biggest performance lever on this silicon (+29.7% measured), and speculative decoding is confirmed as no-gain on Vulkan.** The amdgpu driver pins gfx1013 shader clock at 1500 MHz even under sustained compute; the community SMU governor (firmware calls, no kernel patch) lifts it to 2300+ MHz and TechMakesArt measured +29.7% tg on Qwen3.5-9B Q4_K_M ([Source](https://github.com/TechMakesArt/llama.cpp-bc250)). Speculative decoding on BC-250/Vulkan delivers nothing: a 72% draft acceptance on Llama 3.1 8B+1B still yields identical wall-clock throughput (~55 tok/s both) because the Vulkan batched-verify path is the bottleneck ([Source](https://github.com/TechMakesArt/llama.cpp-bc250)). The spec's speculation plans should be dropped — the flash-moe experiment log independently found MTP speculative decoding break-even for MoE because I/O scales per-token ([Source](https://github.com/danveloper/flash-moe)).

**The gfx1013-vs-RDNA2 Oberon conflict is real and unresolved.** Phoronix reported Cyan Skillfish "is the GFX10/RDNA variant that powers the Sony PS5" and is "basically RDNA1/GFX10" with `image_bvh_intersect_ray` ray-tracing extensions — but akandr/bc250 explicitly states the PS5's Oberon is RDNA 2 (gfx1030+) and the BC-250's gfx1013 "behaves like a GFX10.1-era variant" ([Source](https://www.phoronix.com/news/AMD-RADV-PS5-BC-250), [Source](https://github.com/akandr/bc250)). The "RDNA 1.5" label is informal shorthand. This matters because the TechMakesArt shader wins (rm_kq=4, fused gate+up) are tuned to RADV gfx1013 and may regress on a true RDNA2 Oberon — so the PS5 build must A/B those shader changes on the console itself, not assume BC-250 numbers transfer.

**Confirmed facts that hold:** the loader's memory carve-out is a `vram.txt` kernel cmdline defaulting to 512MB enabling Dynamic VRAM; DF measured ~15 GB usable, full 8 cores/16 threads Zen 2, 36 CU, boost CPU 3.5GHz / GPU 2.23GHz, dynamic graphics "seems to top out at around 5.5GB"; kernel params per the BC250 recipe (`ttm.pages_limit=<GB×1024×1024/4>` + matching `ttm.page_pool_size`; **S5 PRUNE 2026-10-21: the old `amdgpu.gttsize=14750` was a fabricated token — STATE F12/W5**) plus a 40-CU enable "verified working in Linux" are the reference tuning ([Source](https://www.digitalfoundry.net/news/2026/05/playstation-5-linux-tested-steam-pc-vs-native-ps5-games)). The Kraken hardware decompressor is a confirmed hardware feature but **no evidence exists that Linux accesses it** — ps5-linux treats storage as plain NVMe/ext4 with no decompressor driver, so any plan relying on Linux-side hardware decompression is unsupported ([Source](https://github.com/ps5-linux/ps5-linux-loader)). Thermals: `ps5_control` is the only tool, and the guidance is to always enable the fan when boosting — no sustained-load temperature datapoints exist under Linux, so boost-with-fan is the safe assumption ([Source](https://github.com/ps5-linux/ps5-linux-tools)).

## The deciding unknowns, ranked by risk

The build hinges on a short list of measurements, and they rank in this order of risk:

**1. M.2 read throughput under Linux on the PS5 (the project gate).** This is the single unmeasured, deciding unknown — no published figure exists, and it directly determines whether the serial GPU→SSD→GPU pipeline can sustain usable decode. On flash-moe's M3 Max, the SSD read for K=4 experts was 2.41ms of a 4.28ms per-layer pipeline — ~56% of the critical path — and the engine is hardware-optimal as a serial pipeline on unified memory ([Source](https://github.com/danveloper/flash-moe)). On a PS5 with a slower NVMe, SSD read likely dominates even more. If the slot sustains ≥5 GB/s, a 122B-A10B at Q4 (72.8 GB expert data) with K=8 needs ~8 expert loads/token — the arithmetic is feasible but tight. If it sustains ~3 GB/s, the whole approach collapses and you pivot to a smaller model or USB/external. **This is the first measurement to take.**

**2. Whether pLinux5-NG boots on the existing 13.x console and whether M.2 works (a binary, upfront hardware test).** The console is already on 13.x, so firmware is fixed and not an obstacle. pLinux5-NG is 13.20-confirmed and 13.60-experimental, 14.00/14.10 blocked, and its README never mentions M.2 — so M.2 behavior on this path is unconfirmed. The gate is: does the loader boot on this specific 13.x, does amdgpu come up, and does the M.2 slot enumerate as a Linux disk. If M.2 doesn't work on pLinux5-NG, the whole build is dead before it starts.

**3. Whether RADV VK_EXT_external_memory_host is actually available on gfx1013.** The zero-copy landing path depends on it, but it's inferred from RADV's general implementation, not confirmed on this chip. A `vulkaninfo`/CTS check on the console settles it in minutes — low effort, moderate risk.

**4. Hardware decompressor access under Linux.** If the Kraken unit could be driven from Linux, compressed experts would read at ~9.9 GB/s instead of ~5.5 GB/s (EaseUS figures) — nearly doubling effective bandwidth ([Source](https://www.easeus.com/partition-master/ps-5-ssd-speed-test.html)). But no driver exists, so this is speculative upside, not a dependency. Treat it as an opportunistic experiment, not a plan requirement.

**5. Sustained thermals under boost.** No Linux datapoints exist; boost (3.5/2.23 GHz) with fan-on is the safe assumption, but sustained decode is a worst-case thermal load. The 40-CU unlock and SMU-governor-style clock lifting add heat, and there's no published evidence the console holds it without throttling.

**6. Single-node 122B decode figure.** No single-node 122B-A10B number exists on BC-250 — only the 4-node cluster's 29.5 tok/s (with RPC tax) and single-node small-model results (9B at 54.99, Gemma 4 26B-A4B at 69.66) ([Source](https://github.com/ggml-org/llama.cpp/discussions/28226)). The 122B streaming figure is a projection, not a measurement, and the gpt-oss-120b question on gfx1013 is entirely unanswered. This is the last unknown because it's the deliverable's performance ceiling, not its viability gate.

## My recommended plan

Keep the spec's phase skeleton — it's sound — but reorder and add hard gates so the two weekend measurements decide the build before engine code exists.

**Gate 0 (before any engine work): boot pLinux5-NG on the existing 13.x console and prove the platform.** No console purchase is needed — 13.x is the fixed target. Boot pLinux5-NG per its README (13.20 confirmed, 13.60 experimental), confirm amdgpu comes up and the M.2 slot enumerates as a Linux disk, then apply the BC-250-derived kernel tuning (`ttm.pages_limit=4194304` **and** `ttm.page_pool_size=4194304`, plus the ttm pair per RUNBOOK Step 2.6; **S5 PRUNE 2026-10-21: the `amdgpu.gttsize=14750` once quoted here was a fabricated token — STATE F12**), and verify live that `/sys/module/ttm/parameters/pages_limit` reads `4194304` — not the silently-overwritten `3145728` (12 GiB) ([Source](https://github.com/akandr/bc250)). **Go/no-go: pLinux5-NG boots with amdgpu and M.2 working, and GPU memory verifies at 16 GiB. If not, stop — no amount of engine engineering fixes the platform.**

**Gate 1 (the deciding measurement): measure M.2 throughput under Linux, before anything else.** Run `fio` (and `hdparm`/`dd` as cross-checks) on the M.2 partition with the loader's LBA-alignment fix applied. This is the number the spec lacked and the whole build hinges on. **Go/no-go: sustained sequential read ≥5 GB/s on the M.2 slot. If ~3 GB/s, pivot to a smaller model (Qwen3.5-35B-A3B streams at 11.5 tok/s on 16 GB on flash-moe's approach) or an external USB M.2 enclosure, and skip the 100B+ target.** This gate is the single most important thing to do first, and it directly de-risks the serial routing dependency: flash-moe proved the serial GPU→SSD→GPU pipeline is hardware-optimal on unified memory, so the only de-risking lever is knowing the SSD number that feeds it.

**Phase 1 (baseline, reordered to precede the port): establish the llama.cpp-Vulkan-on-RADV baseline and clock unlock.** PS5LM already runs llama.cpp's Vulkan backend on the console via RADV, and gpt-oss GGUF/MXFP4 is natively supported — so this is the proven path, not a gamble ([Source](https://ps5lm.cobanov.dev/), [Source](https://x.com/ggerganov/status/1952779751736627627)). Measure a small dense model (Qwen3.5-9B Q4_K_M) as the calibration point, then A/B the three TechMakesArt shader changes (rm_kq=4, Q4_K smin restructure, fused gate+up+SWIGLU) on the console itself — they were tuned to RADV gfx1013 and may regress on a true RDNA2 Oberon, so the gfx1013-vs-RDNA2 conflict is resolved empirically here ([Source](https://github.com/TechMakesArt/llama.cpp-bc250)). Confirm the 40-CU unlock and clock governor are the single biggest wins (+1.32× gen, +29.7% tg) and that boost-with-fan holds thermally. **Go/no-go: decode scales with clock and CU unlock as expected; if the Oberon is genuinely RDNA2 and the shader changes regress, drop them and keep the governor.**

**Phase 2 (the port): reuse flash-moe/MoE-Direct, don't reinvent.** Port the proven architecture — parallel `pread()` for expert files, "trust the OS" page cache (no custom cache), deferred expert compute, serial pipeline — and adopt MoE-Direct's byte-preserving, per-expert SHA-256 verification for the correctness story ([Source](https://github.com/danveloper/flash-moe), [Source](https://github.com/tmxkzm1925-max/moe-direct)). The research is decisive here: **mmap of expert files is −5x worse than pread on cold data, expert prediction/speculation is net-negative (−18% temporal, −38% speculative early routing), and LZ4 compression is net-negative (−13%)** — so the spec should not invest in expert prediction, compression, or mmap ([Source](https://github.com/danveloper/flash-moe)). Do not port the Apple-silicon-specific optimizations (F_NOCACHE only helps at low bit-widths; SSD-DMA-vs-GPU arbitration is a Mac memory-controller artifact).

**Phase 3 (the 100B+ model): pick the target and the quant empirically.** Two viable targets exist with ready GGUF artifacts: Qwen3.5-122B-A10B (72.8 GB Q4_K_M expert data) and gpt-oss-120b (61 GB MXFP4, native to llama.cpp). Re-benchmark IQ4_XS on the actual build rather than trusting the old −23% figure — it's speed-parity with Q4_K_S on b10727, and the smaller file (43 GiB IQ3_S was the cluster's choice) buys SSD headroom ([Source](https://github.com/ggml-org/llama.cpp/discussions/28226)). The engine cost scales with active-K × experts per token, not model size — flash-moe's K=4 vs tayoun's K=6 shows routing-K is a real dial, so tune K down toward the minimum acceptable quality ([Source](https://github.com/tayoun/flash-moe)). **A/B: Q4_K_M vs IQ3_S/IQ4_XS decode tok/s and quality on the PS5, and K=4 vs K=8 — these are the throughput levers, and they're measurable in an afternoon.**

**Phase 4 (integration): drop speculative decoding, keep the serial pipeline, and treat the decompressor as optional upside.** Speculative decoding is confirmed no-gain on Vulkan (the batched-verify path is the bottleneck) and break-even for MoE — drop it from the roadmap. Keep the serial GPU→SSD→GPU pipeline; it's hardware-optimal on unified memory. If time permits, probe whether the Kraken decompressor can be driven from Linux — if it works, compressed experts nearly double effective bandwidth, but no driver exists so this is opportunistic, not required.

**Phase 5 (QA): correctness before speed.** Use MoE-Direct's byte-preserving verification to guarantee token-identical output against a resident reference, then measure sustained decode and TTFT. **Final go/no-go: coherent output at a sustained rate the user accepts (the BC-250 cluster's 29.5 tok/s is the multi-node ceiling; a single PS5 will land below it — set expectations at 5–10 tok/s on 122B-A10B, or 15+ on a 35B-A3B).**

The one adjustment to the spec's phases: **the M.2 throughput measurement must move to the front, before the engine architecture is finalized** — it's currently an open question, but it's the deciding gate. And the firmware decision is settled (13.x is fixed), so the upfront gate is a hardware test — does pLinux5-NG boot on the existing console and does M.2 work — not a research question.

## Open questions I would still resolve

The research leaves several threads worth pulling before or during the build. **The single-node 122B decode figure on gfx1013-class silicon is the biggest open gap** — only the 4-node cluster's 29.5 tok/s exists, so the PS5's realistic ceiling is a projection, not a measurement; a BC-250 single-node 122B run would bracket it cheaply. **Whether VK_EXT_external_memory_host is actually advertised on gfx1013** needs an on-target `vulkaninfo` check — it's inferred, not confirmed. **Whether the PS5's Oberon is gfx1013 (RDNA1) or gfx1030 (RDNA2)** is unresolved between Phoronix and akandr, and it determines whether the TechMakesArt shader changes transfer — resolve it empirically on the console. **Whether the Kraken hardware decompressor can be driven from Linux** is open and would be the highest-leverage discovery (near-2x bandwidth), but no driver exists. **Sustained thermal behavior under boost with the 40-CU unlock and clock governor** is unmeasured — the console's cooling was designed for Sony's own power management, and no Linux shutdown/throttle reports exist. And **whether pLinux5-NG boots on the specific 13.x revision the console runs** (13.20 is confirmed, 13.60 experimental) **and whether M.2 enumerates on that path** — the README never mentions M.2, so this is the build's real viability gate, and if M.2 doesn't work on pLinux5-NG the project is dead before engine code.
